# i18n 现状与补齐计划

## 现状

`client.js` 里注册了一个 `locale` 命名空间，但字典只有 3 条：

| key | 用途 |
|---|---|
| `tab.title` | 右侧栏 tab 标题 |
| `guide.title` | 引导页卡片标题 |
| `guide.description` | 引导页一句话说明 |

除此之外，面板里约 **160 条文案是硬编码中文**（按钮、菜单项、空态、提示行、`aria-label`、`title`…）。
所以英文用户看到的界面基本仍是中文。README 的「已知限制」里如实写了这一点。

## 两条路，二选一

### A. 补齐（工作量中等，收益明确）

1. 按功能分组把文案搬进 `zh` / `en` 字典（约 160 条）：顶栏、筛选行、卡片、行、排序菜单、文件菜单、
   预览弹窗、toast、空态与错误提示；
2. 渲染处统一改成 `t("card.used", { count })` 这类调用，带插值的用占位符；
3. 插值/复数：中文不分单复数，英文需要 `1 file` / `2 files`，建议 key 里带 `_one` / `_other` 或用
   `Intl.PluralRules`；
4. **验证**：把 `tools/` 下的 harness 固化进仓库（假 ctx + 假 `sidebarRight`/`uiWorkspace` + 一份 fixture），
   用两个 `locale` 各渲染一遍，断言关键节点的文本没有中文残留、没有把 key 直接显示出来。

风险：面板是手写 React（无打包器），文案散在 2100 行里，改动面大；没有 UI 回归之前不建议一次性全搬。

### B. 明确只做中文（工作量 10 分钟）

1. 删掉 `en` 字典，注册时只传 `zh`（或保留 `en` 但只覆盖那 3 条——现状是最不诚实的一种：承诺了英文却只有 3 条）；
2. README 的定位、仓库描述、市场条目都写「中文界面」；
3. 以后要做多语言再按 A 走。

## 建议

先做 **B**（把承诺和现实对齐），把 **A** 排在 `client.js` 拆分（把文案集中到 `lib/client/i18n.js` 更省事）
之后一次性做，并用固化后的 harness 验证两个 locale。

## 需要先补的前置

`tools/` 里目前只有引擎 / 解码 / 路由 / 缓存四支回归，**没有 UI 回归**。A 方案开工前应先提交
`tools/harness/`（我在开发时已经手搓过很多次，形态是固定的：假 ctx + 假 `sidebarRight`/`uiWorkspace`
+ 一份合成 fixture + 一个静态页），否则搬 160 条文案没有安全网。
